# Push Delivery Integrity — 2026-07-30

## Зафиксированная проблема

Expo Push API может вернуть HTTP 200, но отклонить отдельные сообщения через `data[].status = "error"`. Прежняя реализация проверяла только HTTP-статус и после любого 200 возвращала `True`.

Это приводило к следующим ложным состояниям:

- outbox отмечал push как доставленный, хотя Expo его отклонил;
- `DeviceNotRegistered` оставался в базе и использовался снова;
- одинаковые строки `PushToken` создавали повторные уведомления;
- более 100 сообщений отправлялись одним запросом вопреки контракту Expo;
- токен мог оставаться привязанным к прежнему пользователю после смены аккаунта на устройстве.

## Новый контракт

1. При регистрации принимаются только канонические `ExpoPushToken[...]` и legacy `ExponentPushToken[...]`.
2. Один физический токен принадлежит последнему вошедшему пользователю.
3. Существующие дубли токена схлопываются при регистрации.
4. Перед отправкой токены нормализуются и дедуплицируются.
5. Один HTTP-запрос содержит не более 100 сообщений.
6. HTTP 200 не является достаточным доказательством успеха — проверяется каждый ticket.
7. Ticket `ok` обязан содержать receipt ID.
8. `DeviceNotRegistered` считается постоянным отказом: токен удаляется и больше не ретраится.
9. Ошибки credentials, payload, rate limit, malformed response и transport failure возвращают `False` для повторной обработки outbox.
10. Отсутствие токена — успешный no-op, поскольку in-app notification уже является долговечной канонической доставкой.
11. Очистка постоянных токенов выполняется отдельной DB-транзакцией и не коммитит бизнес-состояние вызывающего процесса.

## Регрессионные гарантии

`backend/tests/test_push_delivery_integrity.py` проверяет:

- no-token no-op;
- дедупликацию;
- чанки 100/100/5;
- сохранение payload/outbox identity;
- permanent cleanup;
- HTTP 200 с ticket error;
- request-level Expo errors;
- malformed ticket cardinality;
- отсутствующий receipt ID;
- network failure;
- валидацию токена;
- перенос токена между пользователями;
- схлопывание дублей регистрации.

Тест включён в обязательный backend CI gate. В тот же gate дополнительно закреплён `test_storage_integrity.py`, который ранее выполнялся в PR, но не был перечислен в постоянной команде pytest.

## Следующий уровень

Ticket подтверждает только принятие сообщения Expo. Полноценный receipt worker должен отдельно запрашивать Expo receipts, фиксировать окончательный provider outcome и удалять `DeviceNotRegistered`, обнаруженные уже на этапе APNs/FCM.
