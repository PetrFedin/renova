# 13. Живой сквозной сценарий (API, in-process): «новые пользователи» от регистрации до корзины

Дата прогона: 2026-09-30. Срез: полный жизненный цикл ремонта через HTTP API, пройденный по шагам 1–14 задания как **новыми** пользователями (не демо-данные).
Скрипт: `docs/audit-map/journey-script-13.py` (167 шагов, 530 HTTP-вызовов, 24 фазы). Продуктовый код не менялся; живой backend `127.0.0.1:8100`, Expo `:8081` и Docker не затрагивались.

## 0. Как проверялось

- **Среда**: `pytest`-совместимый скрипт (`python -m pytest ../docs/audit-map/journey-script-13.py -s` из `backend/` либо `python journey-script-13.py`), ASGI-клиент `httpx.ASGITransport` поверх `app.main:app`, **изолированная SQLite** во временном каталоге (`init_db()` → пустая база без `ensure_demo_users`), ровно как фикстуры `backend/tests/test_contract_gate_golden_path.py` / `test_e2e_flow.py`, но **без** демо-сидов: пользователи создаются через `POST /auth/sms/send` + `POST /auth/sms/verify` (в dev SMS-провайдер не настроен, ответ содержит `preview:true, demo_code`), авторизация — `Bearer` JWT (не `X-User-Id`).
- **Действующие лица**: заказчик; исполнитель (lead); чужой исполнитель (`contractor2`, «не подключён»); наблюдатель (customer-роль, добавленный через `POST /projects/{id}/viewers` по `profile_code`); исполнители 3–7 для побочных проектов (лимит free-плана: 1 проект на исполнителя); прораб команды. Побочные проекты: B (самозахват), S (заказчик без исполнителя), T (подпись одной стороны), U (гейт без договора), X (чужие строки сметы), маркетплейс-заявка.
- **Не повторяет** существующие e2e: `project-lifecycle.spec.ts` (create/archive/trash/restore, права подрядчика на lifecycle), `room-lifecycle.spec.ts` (комнаты), `change-order-lifecycle.spec.ts` (роли/бюджет/replay CO), `contract-gate-path.spec.ts` (lock → подпись → старт), `customer-path.spec.ts` (демо-проход). Этот прогон идёт дальше: регистрация с нуля, состояние «до/после подключения», обе стороны договора, график, старт/сдача/возврат/приёмка, платёж→чек→спор→evidence, CO→документ→оплата, закупка, closeout, гарантия, purge, команда/маркетплейс/чат-приглашение, а также негативные ветки на каждом шаге (чужой, не подключённый, гость, повтор, отказ).
- **Важное наблюдение про тесты**: `backend/tests/test_contract_gate_golden_path.py` и `e2e/contract-gate-path.spec.ts` подписывают договор **только заказчиком** и утверждают, что после этого этап стартует, — то есть дефект JRN-002 зафиксирован тестами как «ожидаемое поведение». Оба e2e-спека (`room-lifecycle`, `change-order-lifecycle`) перед `assign` вызывают `POST /subscription/checkout` за исполнителя — обход скрытого условия JRN-010.

## 5. «Тупящие» места и скрытые предусловия (сводка)

1. Пока исполнитель не создал публичный профиль, заказчик не может его подключить (JRN-013).
2. Договор существует только после `propose-lock` → `lock`; до этого гейт «нет договора» пропускает, а старт — нет (JRN-012).
3. «Подписан обеими сторонами» не проверяется (JRN-002).
4. Второй проект исполнителя требует Pro; ошибку получает заказчик (JRN-010).
5. Сдача этапа: чек-лист 100 % **и** фото с «правильной» подписью или ≥2 фото; после возврата часть пунктов сброшена (JRN-016, шаг 113).
6. Закрытие проекта: 8 pending-платежей → только «подтверждение» без оплаты (JRN-008).
7. Спор, evidence-ревью — только один заказчик/админ (JRN-020/021).
8. Success-API, не меняющий то, что видит другая роль: подключение исполнителя (нет уведомлений), платёж (budget_spent 0), progress_percent, приёмка (замечания open), purge (уведомления с мёртвыми ссылками).

## 6. Не проверяемо без внешней системы (поведение в dev)

- Внешняя e-sign: `POST /documents/{id}/sign {provider: kontur|goskey}` → 501 `esign_provider_unavailable` (`GET /esign/providers`: доступен только `in_app`); вебхуки/`/esign/dev/kontur/simulate` не прогонялись.
- ФНС-проверка чека: `GET /fns/health` → `verification_mode: unavailable`, `demo_verify_allowed:false`; чек сохраняется `verification_pending` («Проверка ФНС не настроена»); «Мой налог» `oauth/start` → 503 `moy_nalog_not_configured` (нужны `MOY_NALOG_*`, `REDIS_URL`).
- ЮKassa: для pending-платежей demo-режим (`payments_mode: demo`) сразу «оплачивает» через собственный webhook-обработчик; live-режим не проверялся (`GET /subscription/yookassa/health`).
- SMS: OTP в dev — `preview:true, demo_code` в ответе (`otp_service.py`, `sms_service.py`); в staging/production без Twilio отправка вернёт `503 SMS не настроена`.
- Не покрыты этим прогоном: портал (`/portal/**`, `POST /auth/portal/session`), технадзор, Telegram/push, WebSocket, marketplace `auto-assign`, работа с загрузкой файлов/OCR документов, календарь-ICS.
