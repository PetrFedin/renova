## Purpose

This radar keeps Renova from turning research into uncontrolled scope.

Every candidate is evaluated against five questions:

1. Does it reduce real user work or decision latency?
2. Does it compound Renova's evidence/authority moat?
3. Can it create premium/enterprise/network revenue?
4. Can it be introduced without creating a second business authority?
5. Is the technical/operational risk proportional to the value?

## Scoring

Each candidate receives 1–5 scores:

- **UX** — day-to-day user value;
- **Moat** — proprietary compounding/history/network value;
- **Revenue** — premium/enterprise/marketplace leverage;
- **Readiness** — fit with current Renova authorities/data;
- **Risk** — technical/privacy/false-truth complexity, where 5 = highest risk.

Priority heuristic:

`priority = UX + Moat + Revenue + Readiness - Risk`

The number is a planning aid, not an automatic product decision.

## Competitive gap mapping

### OpenSpace direction

Observed public direction:

- live indoor/location-aware Site Mode;
- autolocation without dedicated beacons;
- voice field capture;
- live capture coverage;
- visual progress;
- progress APIs / agent ecosystem;
- forecasting over reality data.

Renova response should not clone the capture product. Its advantage should be:

`reality capture -> evidence -> room/work authority -> inspection -> acceptance -> payment/warranty -> Verified Execution Record`

That is a deeper transaction/evidence chain than a visual-only layer.

### Buildots direction

Observed public direction:

- measured progress;
- delay/risk intelligence;
- AI project assistant;
- management analytics.

Renova response:

- keep forecasting explainable and tied to accepted/observed evidence;
- retain actual-vs-plan and confidence lineage;
- connect risk to RFI/Submittal/material/hold-point/acceptance facts;
- keep prediction separate from authority.

### Procore / Autodesk direction

Observed public direction:

- AI assistant/coworker embedded where project data lives;
- task-specific agents/skills;
- connected AEC lifecycle data.

Renova response:

- no generic chatbot;
- project-specific cited retrieval;
- bounded copilots that prepare existing Renova commands;
- organisation-specific Skills/Playbooks;
- AI action receipt for every high-value proposal.

## Visual advantage strategy

Renova should look **calm, architectural and evidence-first**, not like generic ERP.

### Core visual principles

1. One primary decision per view.
2. Spatial context when it materially helps.
3. Dense facts through progressive disclosure.
4. Quiet surfaces, sharp hierarchy.
5. Media/evidence is large where proof matters.
6. Warnings are semantic, not decorative.
7. Motion explains state/context, never hides pending/error.
8. Same authority projected differently by role.

### Monitor mode

- persistent project/nav rail;
- large central canvas/list;
- decision/evidence rail;
- keyboard shortcuts/search;
- compare/timeline views.

### Tablet mode

- split list/canvas;
- collapsible inspector;
- field review/presentation;
- pen/markup friendly geometry.

### Phone mode

- one-handed capture;
- one primary action;
- bottom sheets;
- minimal nested navigation;
- always-visible offline/queue status.

## What Renova should explicitly avoid

- generic LLM chatbot on every screen;
- auto-acceptance from computer vision;
- auto-payment from measured progress;
- full-app CRDT;
- separate vector database before PostgreSQL/pgvector is insufficient;
- separate BIM/project/document authorities;
- mandatory LiDAR;
- photorealistic 3D as a blocker for ordinary workflows;
- opaque contractor "AI score";
- false precision in forecasts;
- visual redesign that replaces existing clear slate/blue identity with fashion-driven effects.

## Kill criteria

A research item is stopped or deferred when:

- it creates a second authority;
- required data quality is not available;
- users cannot explain why it helps;
- latency/battery/memory regression exceeds the measured benefit;
- privacy/ACL risk cannot be bounded;
- a simpler existing Renova workflow performs equally well;
- the feature is impressive in demos but does not improve completion, quality, trust or revenue.
