# RENOVA — квалификация исправления чатовых команд

Дата: 2026-09-09. Родитель: `CHAT-BUSINESS-COMMAND-CONTRACT.md` и `../RENOVA-TECHNICAL-SPECIFICATION.md`.
Статус: IMPLEMENTED / EXACT-HEAD CI REQUIRED. PR #322, ограниченный участок #316.
Приоритет: завершить существующий P0 hotfix; новые функции и активация провайдеров в этот PR не входят.

## 1. Исправление тестового окружения

На `618ea52145c85c1ecf2a70a1b8aad34087ae525c` workflow `34282353308` прошёл серверную часть `command-contract` с PostgreSQL, но мобильная часть остановилась до выполнения бизнес-сценариев. Причина: `esModuleInterop: false`, несовместимое с закреплённым TypeScript 6.0.3. Локальный прогон другим компилятором не является доказательством канонического CI.

В `scripts/chatBusinessCommandTransport.test.mjs` включён поддерживаемый interop; модель AsyncStorage явно объявляет ES-module default. Версия компилятора сверяется с его реальным workspace-путём в package-lock. Подстановка глобального TypeScript другой версии больше не допускается. Диагностика содержит имя файла, версию и код ошибки. Негативная проверка обязана отклонить намеренно неверный TypeScript: диагностика не подавляется.

Все 30 прежних сценариев сохранены без ослабления assertions. Исполняются реальные req, producer, очередь и flush; симулируются только сеть, platform storage и телеметрия. Это не проверка физического телефона и не операция внешнего провайдера. Gate `34287912451` на `ca46f57036e27b5609f7b69fe0347a7c78e608eb` подтвердил исправление тестового загрузчика; последующие изменения требуют отдельного полного прогона.

## 2. Точечное обновление парсеров

Первый security gate `34282353223` обнаружил новые для действующего baseline high advisory в двух транзитивных экземплярах XML-парсера. После их исправления повторный audit `34288797480` выявил отдельный high advisory `GHSA-2883-xcg3-v3hh` в js-yaml. Исключения не расширялись; production audit не отключался.

Изменены ровно три существующие записи package-lock, только version/resolved/integrity:

| Запись | До | После |
|---|---|---|
| node_modules/@xmldom/xmldom | 0.8.13 | 0.8.15 |
| node_modules/plist/node_modules/@xmldom/xmldom | 0.9.10 | 0.9.12 |
| node_modules/js-yaml | 4.3.1 | 4.3.2 |

Точные npm metadata и integrity сверены до установки. Декларации пакетов, количество узлов, зависимости, лицензии и прочие поля lock не меняются. Ни npm audit fix --force, ни обновления «до latest» не используются.

Первоисточники: https://github.com/xmldom/xmldom/releases/tag/0.8.15 ; https://github.com/xmldom/xmldom/releases/tag/0.9.12 ; https://github.com/nodeca/js-yaml/security/advisories/GHSA-2883-xcg3-v3hh ; https://github.com/nodeca/js-yaml/releases/tag/4.3.2 .

`scripts/xmldomIntegrity.test.mjs` проверяет обе установленные версии, XML escape/русский текст, ограниченный HTML raw-text regression и реальные потребители @expo/plist и plist. У Expo проверяется фактический default export. Нормализация только прототипов словаря допускает безопасные null-prototype objects; значения, числа, логические поля, массивы, Buffer и Date сверяются строго.

`scripts/yamlParserIntegrity.test.mjs` проверяет закреплённую версию, сериализацию данных и расход лимита maxTotalMergeKeys на трёх пустых источниках слияния. Нормальный документ принимается, тот же документ с лимитом 2 отклоняется YAMLException. Большой атакующий payload и ненадёжный таймер не нужны.

Эта проверка не сертифицирует произвольный пользовательский XML/YAML. Новые входные пути требуют отдельной валидации и лимитов. Существующие временные исключения image-size и moderate findings не объявляются устранёнными.

## 3. Встраивание в существующие CI-проверки

На main появился `PRODUCT-COMPLETION-MANDATE.md`, запрещающий новые постоянные workflow. Квалификация перенесена в уже существующие файлы, без удаления тестов:

- `ci.yml / mobile-contracts`: реальные 30 сценариев транспорта и XML/plist, после locked npm ci;
- `ci.yml / chat-message-contracts`: все прежние chat-тесты плюс chat business commands и шесть реальных PostgreSQL сценариев на той же мигрированной базе; отдельный CHAT_COMMAND_POSTGRES_URL;
- JUnit guard запрещает пустой прогон, любой skip/error/failure и отсутствие полного набора из шести PostgreSQL сценариев;
- `js-dependency-integrity.yml`: ограниченный YAML regression, прежний audit и его отрицательная проверка без изменений;
- канонический Playwright API-список уже содержит `e2e/chat-business-command.spec.ts`.

Новые отдельные chat/XML workflow и одноразовый механизм подготовки lock удалены из итогового дерева PR. Их сценарии не потеряны. `grep -R -n -E 'chat-business-command-integrity|xml-parser-integrity|agent-qualify-xmldom' docs scripts .github` на исходном дереве находил только self-trigger строки удаляемых workflow; обработчиков продукта с такими именами нет. Самостоятельные скрипты и все tests/test_chat_business_commands* сохранены и явно запускаются существующим CI.

Код новых provider ports и общий мандат из main не перезаписываются. Итоговая квалификация PR должна учитывать актуальную базу main; при её изменении требуется повторная проверка. GP3/GP5/GP8 получают ограниченные prerequisite-тесты, а не автоматически зелёный статус полного Golden Path.

## 4. Доказательства и границы

Для предыдущего кандидата `618ea521` сохранён full-backend artifact `10078307376` запуска `34282353232`: 1090 passed, 24 skipped, 139 warnings. Это baseline этого квалификационного прохода, а не новая проверка итогового кандидата. Шесть новых PostgreSQL сценариев среди skips общего SQLite-прогона должны исполняться без skips в PostgreSQL job; новый JUnit guard это проверяет.

Окончательные числовые результаты, точный head и идентификаторы запусков фиксируются в Evidence PR после завершения, а не предсказываются в этом документе. Канонический local Docker runtime и физические устройства в текущем контейнере не квалифицированы. Успешный CI не выдаётся за local/device/provider/production проверку.
