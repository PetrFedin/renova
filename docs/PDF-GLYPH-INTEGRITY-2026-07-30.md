# PDF glyph integrity — 2026-07-30

## Problem

Renova PDF exports used the first available Unicode font without checking its character map. The repository contains `ArialUnicode.ttf`, but CI showed that the embedded font did not contain the Russian rouble sign (`₽`). FPDF therefore emitted a missing-glyph warning and the exported estimate/report could lose the currency symbol.

The same class of defect could affect bullets, long dashes, multiplication signs, numero signs, arrows or check marks.

## Rendering contract

The shared `pdf_helper` now:

1. discovers available candidate fonts;
2. reads each font cmap through FontTools;
3. chooses the candidate with the best coverage of the key Renova character set;
4. records all supported code points;
5. sanitizes every line before it reaches FPDF.

A character is passed to the Unicode font only when its code point exists in the selected cmap. Unsupported characters receive readable replacements:

- `₽` -> `руб.`;
- bullet -> `-`;
- en/em dash -> `-`;
- multiplication sign -> `x`;
- numero sign -> `No.`;
- arrows -> ASCII arrows;
- check/cross marks -> `[x]`.

Cyrillic is transliterated only when no usable Unicode glyph exists. Unknown unsupported glyphs become `?`, so FPDF never receives a code point that the selected font cannot render.

## Failure modes

- Missing or unreadable fonts do not crash application startup; the helper falls back to Helvetica and ASCII/transliteration.
- Font cmap parsing is cached and performed once per file.
- A broken candidate is treated as unavailable rather than selected.
- PDF output remains valid and begins with the PDF header.

## Regression tests

`backend/tests/test_pdf_glyph_integrity.py` verifies:

- readable currency/transliteration fallbacks;
- the sanitized output contains only renderable code points;
- PDF generation succeeds with Cyrillic and special symbols;
- no Python warning or log record contains `missing glyph`;
- generated bytes contain a valid `%PDF-` header.

The test is part of the mandatory backend CI gate.
