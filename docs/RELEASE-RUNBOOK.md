# Renova — runbook релиза и отката

Статус: процедура. Продакшен-среды пока нет (`PRODUCTION-READINESS.md`, блокер E6), поэтому команды ниже описывают целевой порядок, а проверенные части отмечены явно. Не выдумывайте значения: хост, digest, ключи подставляются из вашей среды.

Область: backend (`renova-api` + `renova-worker`, один образ) и мобильное приложение (EAS). Основа: `docs/STAGING-RELEASE.md`, `docs/RUNTIME-TOPOLOGY.md`, `docs/DISASTER-RECOVERY.md`.

## 0. Роли

| Роль | Делает |
|---|---|
| Release owner | Решает go/no-go, ведёт запись релиза, подтверждает откат |
| DevOps | Образ, миграции, деплой, бэкапы, алерты |
| Бэкенд/Мобайл | Исправления вперёд, анализ инцидента |
| Дежурный | Принимает алерты первые 24 часа после релиза |

Конкретные люди назначаются до релиза и записываются в запись релиза (§8).

## 1. Правила

1. Релиз — это пара: **Git SHA + digest образа** (`ghcr.io/petrfedin/renova-api@sha256:...`). Тег `latest` и пересобранный образ релизом не являются.
2. API и worker запускаются из **одного digest**, на обоих `RENOVA_IMAGE_DIGEST=sha256:<64 hex>`.
3. Схема меняется только через Alembic. `ALLOW_CREATE_ALL` и `ALLOW_DEMO_SEED` в рабочих средах запрещены и валят старт.
4. Откат приложения не откатывает схему (см. §6). Миграции пишутся совместимыми со старой версией приложения хотя бы на один релиз.
5. Никакие секреты не записываются в запись релиза и не печатаются в логах.

## 2. До релиза (T-1 день)

- [ ] Чек-лист §4 в `PRODUCTION-READINESS.md` пройден до пункта «образ».
- [ ] CI на release-коммите зелёный: workflow `CI`, `Backend image integrity`, `Renova technical specification integrity`, `Database restore integrity`, `Worker runtime heartbeat integrity`.
- [ ] Есть свежий бэкап production-БД и проверено, что он существует (`docs/BACKUP-POLICY.md`, §5). Время бэкапа записано.
- [ ] Записан **предыдущий** рабочий digest и SHA (цель отката).
- [ ] Просмотрен список миграций между предыдущим и новым SHA: `git diff <prev>..<new> --stat -- backend/alembic/versions`. Для каждой новой ревизии решено: совместима ли старая версия приложения со схемой (если нет, откат = восстановление БД, см. §6.3).
- [ ] Заполнены обязательные переменные по `backend/.env.production.example` (проверка: `python -m app.core.runtime_preflight` на новом образе, шаг 3.2).
- [ ] Статус интеграций снят: `python3 scripts/integrations-status.py` (`GET /api/v1/admin/integrations/status`), критичные в состоянии `configured`; пошагово — `docs/INTEGRATIONS.md`. S3 (C9), `CORS_ALLOWED_ORIGINS` без `*` (C10) и `FORWARDED_ALLOW_IPS` (C11) теперь проверяются кодом при старте production; вручную остаётся убедиться, что в `FORWARDED_ALLOW_IPS` именно адреса вашего балансировщика, а не `*`.
- [ ] Согласован дежурный на 24 часа после релиза.

## 3. Релиз backend

Выполняется DevOps. Шаги идут строго по порядку; на любом провале останавливаемся и идём в §6.

### 3.1 Образ

Образ собирается workflow `Backend image integrity` из SHA релиза. Записать: `release_sha` (40 символов) и `image_digest` (`sha256:...`). Не пересобирать.

### 3.2 Миграции и preflight (одноразовые задачи тем же образом)

```bash
# миграция схемы тем же digest
alembic upgrade head
# проверка рабочей конфигурации; печатает только статусы, без секретов
python -m app.core.runtime_preflight
```

Если `runtime_preflight` не OK, релиз не продолжается. Для API проверка «схема на head» выполняется и при старте командой `python -m app.db.migration_guard` (в compose она стоит перед `renova-api`/`renova-worker`).

### 3.3 Запуск процессов

1. Worker: команда `renova-worker`, минимум один экземпляр, тот же digest.
2. API: команда `renova-api` (порт `8100`), тот же digest, `FORWARDED_ALLOW_IPS` задан.
3. Подождать, пока HEALTHCHECK образа станет healthy (`start-period` 30 с).

### 3.4 Проверка снаружи

```bash
curl -fsS https://<API_HOST>/health
curl -fsS https://<API_HOST>/ready
API=https://<API_HOST> python3 scripts/release-smoke.py   # read-сценарий, ничего не пишет
```

Ожидается: `/health` — `status=ok`, `environment=production`, `release` = SHA релиза, `artifact_digest` = digest, `background_runtime=renova-worker`; `/ready` — `status=ready`. В production demo-аккаунтов нет, поэтому read-сценарий проверит только живость и защиту аутентификации; это ожидаемо.

Полный write-сценарий (`--write`) в production **не запускается**: он создаёт пользователей и проект и отказывается работать вне development/test. Его прогоняют на одноразовой среде того же образа до релиза (см. `scripts/release-smoke.py`).

Далее запустить GitHub workflow `External staging release` (для staging) либо его production-аналог с `release_sha` и `image_digest`: он проверяет SHA/digest у API и у живого worker, готовность БД и Redis, владение циклом outbox.

### 3.5 Наблюдение 30 минут

- Sentry: нет всплеска новых ошибок; OTLP-трейсы идут.
- Нет 5xx выше обычного; нет `rate_limit_backend_unavailable` (признак недоступного Redis).
- Worker: в логах `renova worker started tasks=domain_outbox,...`, нет `Traceback` и `worker task crashed`; heartbeat виден в `/api/v1/admin/release-health`.
- Очередь outbox не растёт (dead-letter admin-экран).

Если всё чисто, релиз backend завершён; запись в §8.

## 4. Релиз мобильного приложения

Предусловия: закрыты C1–C4 из `PRODUCTION-READINESS.md` (реальный API URL, `android.package`, `projectId`, данные для `submit`).

1. Preflight: `npm run testflight:preflight` (для CI: `bash scripts/testflight-preflight.sh --ci`).
2. Сборка: GitHub workflow `EAS Build & Submit`, профиль `production` (`submit=false` для первой сборки). Версия берётся из `app.json`, номер сборки инкрементируется EAS (`appVersionSource: remote`, `autoIncrement: true`).
3. Записать ID сборки EAS. Без ID сборка не считается релизной.
4. Установить сборку на реальное устройство; пройти: вход по SMS, создание проекта, загрузка фото, push-уведомление, оплата (в тестовом режиме магазина).
5. Отправка в стор: тот же workflow с `submit=true` по ID сборки, затем ревью стора. Сроки ревью внешние.
6. Поэтапная выдача: после одобрения включить поэтапную выдачу, если стор позволяет.

Порядок между backend и клиентом: **сначала backend** (обратно совместимый с уже установленными клиентами), затем клиент. Старые клиенты остаются в обращении недели, поэтому API не должен ломаться для предыдущей версии.

## 5. Критерии отката

Откатываем при любом из:

- `/ready` не `ready` дольше 5 минут после запуска;
- доля 5xx на публичном API выше 5% в течение 5 минут;
- worker не держит heartbeat или цикл outbox упал и не восстанавливается перезапуском;
- подтверждённое повреждение или потеря данных (платежи, акты, подписи) — сначала остановить запись (§6.3);
- критический дефект безопасности.

Решение принимает release owner. Любое сомнение в целостности финансовых данных — это §6.3, а не повторный запуск.

## 6. Откат

### 6.1 Приложение (основной путь)

Откат приложения — это возврат к **предыдущему digest**, схема остаётся как есть.

1. Остановить новые экземпляры worker, затем API.
2. Запустить предыдущий digest для worker и API (на обоих `RENOVA_IMAGE_DIGEST` = предыдущий).
3. Проверить §3.4 для предыдущего SHA/digest.
4. Записать инцидент и причину.

Работает только если предыдущая версия совместима с уже применённой схемой. Это проверяется на шаге «До релиза» (список миграций).

### 6.2 Схема

`alembic downgrade` **не является штатным откатом**: в репозитории ревизии содержат `downgrade()`, но CI проверяет цепочку вниз только для календаря и push-квитанций. Порядок действий:

1. Предпочтительно: исправление вперёд (новая ревизия поверх head) и выпуск нового образа.
2. Если нужно отменить именно последнюю миграцию, это решение release owner + бэкенд-разработчика: downgrade выполняется на копии БД (восстановление из бэкапа на изолированную среду), результат проверяется, и только потом повторяется в production в окне обслуживания. Миграции, удаляющие или преобразующие данные, вниз не откатываются без потери.

### 6.3 Данные

Если данные повреждены или потеряны:

1. Остановить запись: перевести API в обслуживание (остановить API и worker), чтобы не накапливать новые изменения поверх повреждения.
2. Определить момент последних корректных данных.
3. Восстановить **в отдельную** БД по `docs/BACKUP-POLICY.md` §6 (PITR на выбранную точку), не поверх живой.
4. На восстановленной БД: `alembic upgrade head` при необходимости, `python -m app.core.runtime_preflight`, затем `/ready` приложения против неё.
5. Согласовать с release owner переключение (смена `DATABASE_URL`), записать RPO/RTO фактические.
6. Файлы в S3: восстановление версионированных объектов (BACKUP-POLICY §4). Расхождение БД и объектов — известный риск (#238): после восстановления сверить ссылки на файлы.

### 6.4 Мобильное приложение

Опубликованную сборку из стора нельзя «откатить»: можно остановить выдачу и выпустить исправление с новым номером сборки. Поэтому критичные клиентские дефекты закрываются совместимыми изменениями backend (feature-флаги серверной стороны, ответы с честными ошибками), а OTA в проекте не настроен (C8). Заранее подготовьте минимальный hotfix-процесс: ветка → `EAS Build & Submit` → ожидаемое время ревью стора.

## 7. После релиза

- [ ] 24 часа дежурства; все алерты разобраны.
- [ ] Бэкап сделан после релиза и виден в списке.
- [ ] Обновить `docs/production-readiness-evidence.json` (digest, SHA, run id, build id) в отдельном коммите.
- [ ] Заметки релиза опубликованы (`docs/RELEASE-NOTES-FIRST-RELEASE.md`), `CHANGELOG.md` обновлён.
- [ ] Разбор проблем: что сломалось, что поймал бы smoke, что добавить.

## 9. Что здесь не проверено

- Деплой на реальную платформу не выполнялся: платформа не выбрана (E6).
- Откат на предыдущий digest в реальной среде не отрабатывался.
- Production `External staging release` аналог не существует; используется существующий staging-workflow как образец.
- Длительность восстановления (RTO) измерена только на синтетической БД в CI.
