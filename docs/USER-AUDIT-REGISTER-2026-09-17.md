# Реестр дефектов: сквозной пользовательский аудит, 2026-09-17

Семь параллельных обходов продукта с позиции пользователя — заказчика и подрядчика:
смета, приёмка, документы и портал, деньги, материалы и закупки, график, навигация,
чат и уведомления. Проверка велась на живом стенде (API `127.0.0.1:8100`, демо-данные),
а не только чтением кода.

**Как читать.** Каждая находка имеет серьёзность, категорию, точное место, сценарий
пользователя и доказательство. Колонка «подтверждено» означает, что поведение наблюдалось
живьём — запросом, трассировкой с сервера или на экране. «Вероятно» означает вывод из кода,
не воспроизведённый.

**Чего здесь нет.** Стиля кода, типизации и предложений отрефакторить. Только то, что
ломает или искажает работу пользователя.

---

## Состояние демо-данных после аудита

Обходы включали записывающие запросы, поэтому локальная демо-БД изменена. Перед
дальнейшей работой её стоит пересеять.

| что | где | обратимо |
|---|---|---|
| три строки сметы `AUDIT TEST LINE`, `AUDIT, запятая 60x60`, `AUDIT ROUNDTRIP` | `fa5eea28` | **нет** — см. Б-14 |
| прогресс этапа «Подготовка» сброшен 90 % → 0 % | `fa5eea28` | нет, только правкой в БД |
| два допсоглашения «Доп. розетки» по 8 500 ₽ (`approved` + `pending`) | `fa5eea28` | следствие Б-13 |
| тестовые счета, чеки, две строки из банковской выписки | `fa5eea28`, `aec51466`, `0a0e6b7b` | частично |
| переименование проекта | `0a0e6b7b` | восстановлено |

`aec51466` имеет `estimate_locked_at = 2026-09-17T14:31`, что предшествует аудиту —
приписать его обходам нельзя.

## Блокеры

### Б-1. `GET /os/budget` падает с 500 на любом проекте, где есть закупка

**Место.** `backend/app/services/budget_service_legacy.py:269` (`_single_purchase_field`),
вызов из `backend/app/services/budget_service.py:267` (`expense_from_purchase`),
запрос без `selectinload` — `budget_service_legacy.py:379-388`.

```python
def _single_purchase_field(purchase: Purchase, field: str) -> str | None:
    values = {value for item in (purchase.items or []) if (value := getattr(item, field, None))}
```

`purchase.items` — ленивая связь, а функция синхронная и подгрузить её не может.
В async-сессии это `sqlalchemy.exc.MissingGreenlet`. Работает только когда объекты
случайно уже в identity map, поэтому на одном проекте 200, на другом 500.

**Что ломается.** Все ledger-эндпоинты проекта: `os/budget`, `os/budget/lines`,
`os/expenses`. Оплата через ЮKassa откатывается — `POST /payments/{id}/yookassa-checkout`
отдаёт 500, платёж остаётся `pending`.

**Доказательство.** Трассировка снята с сервера, воспроизведено на двух независимых
инстансах:

```
fa5eea28 (1 закупка delivered):  os/budget 500 · os/budget/lines 500 · os/expenses 500
                                 payments 200 · receipts 200 · dashboard 200
aec51466 (0 закупок):            os/budget 200
```

**Воспроизведение с нуля** на чистом проекте, семь шагов:

```
STEP 0  baseline                os/expenses → 200
STEP 5  закупка в draft         os/expenses → 200
STEP 6  status = delivered      delivered · paid_at None · ordered_at None
STEP 7  после доставки          os/expenses → 500      ← навсегда
```

Радиус поражения на проекте с доставленной закупкой: `os/expenses`, `os/budget`,
`os/budget/lines`, `analytics/expenses-summary`, `analytics/expenses.csv` — все 500;
сам список `purchases` — 200.

**Починка.** Добавить `selectinload(Purchase.items)` в запрос
`backend/app/services/budget_service_legacy.py:381`.

**Почему не поймали тесты.** В тестах `Purchase` создаётся в той же сессии, `items`
уже в identity map, ленивой догрузки не происходит. В свежей сессии HTTP-запроса —
происходит всегда.

**Подтверждено** тремя независимыми обходами.

### Б-3. Ссылка «только просмотр» даёт доступ к другим объектам

отдельно и откачено).

### Б-4. Ссылка на портал ведёт на 404

### Б-19. Сообщение, отправленное без связи, теряется

**Место.** `apps/mobile/lib/api/chats.ts:282`.

Восемь методов чата используют `if (e instanceof ApiError && e.status >= 400 && e.status < 500) throw e;`

### Б-20. Протухшая сессия подменяется демо-аккаунтом

**Место.** `apps/mobile/lib/context/RenovaContext.tsx:447`, `:457-462`.

При 401/403 от `/auth/me` приложение стирает сессию и сразу вызывает `recoverDemoSession()`.

**Подтверждено** (поведение при выключенном демо-режиме — вероятно).

### Б-21. Офлайн-очередь переживает выход и досылается под чужим токеном

**Место.** `apps/mobile/lib/context/RenovaContext.tsx:684` (logout),
`apps/mobile/lib/api/client.ts:288-293` (`authHeaders`).

`logout()` чистит `userId`, `userRole`, `projectId`, токены и снимок, но не трогает
`renova_offline_queue`. При следующем старте `flushOfflineOutbox()` проигрывает старые
задания, а `authHeaders(job.userId)` возвращает **текущий** токен и параметр игнорирует.

задания получают 403 и застревают в `blocked` навсегда — новый пользователь видит чужие
непрошедшие действия, которые не может ни выполнить, ни понять.

**Подтверждено.**

## Что проверено и работает

Чтобы реестр не читался как «всё сломано» — перечень проверенного и исправного.

**Расчёты.** `budget_planned` = Σ (qty × price) + Σ одобренных ДО сходится до копейки
(22 строки → 185 937,70 ₽, пересчитано вручную); используется `Decimal` с `ROUND_HALF_UP`,
потерь на округлении нет. Геометрия комнат верна: 4,2 × 3,1 = 13,02 м² пола,
периметр 14,6 × 2,7 − 2,0 = 37,42 м² стен. Запас материала (ламинат ×1,08) соответствует
`packages/calc-engine`. Суммы закупки сходятся с `total_amount`. Арифметика `delay_days`
корректна и отрицательных значений не даёт.

**Идемпотентность.** Повторный POST с тем же `client_request_id` возвращает тот же id —
для сообщений, строк сметы, счетов, чеков и импорта выписки, включая гонку из четырёх
параллельных запросов. Подмена содержимого при том же ключе даёт 409. Повторное подписание
документа возвращает существующую подпись с `replayed: true`.

**Права.** Правка сметы — только исполнитель, фиксация — только заказчик, `propose → lock`
обязателен. Исполнитель не может confirm и dispute платежа. Посторонний получает 403.
Чужой проект отдаёт 404, а не 403 — факт существования не утекает. Чужой тред чата — 404,
чужой курсор прочтения — 409.

**Переходы состояний.** `start_stage` отбивает неверный статус и неверного актора в
правильном порядке. `completion_check` полон: исполнитель, чек-лист, фото, критичные
замечания, материалы, зависимости. Спор по платежу — не тупик для заказчика. Удаление
расхода, связанного с источником, блокируется 409.

**Офлайн.** Одна каноническая очередь, миграция legacy-ключей, блокировка при мутациях,
версионирование против гонок, экспоненциальный backoff, 409 → ручной разбор, ≥5 попыток →
видимый `blocked`. Дублей при повторной синхронизации нет.

**Навигация.** 69 маршрутов сверены с целями навигации в обе стороны; кроме Б-12 и Б-22
разрывов нет. Все `link_path` бэкенда резолвятся в существующие маршруты. Неизвестный slug
даёт честный экран с двумя рабочими кнопками. Нижняя навигация не может отрисовать мёртвую
кнопку. Пустые состояния дисциплинированы — 72 использования `EmptyActionState`.

**Экспорт.** Все семь PDF отдают валидные файлы с корректным `Content-Type`; кириллица
рендерится и копируется (встроен субсет `ArialUnicodeMS` с `ToUnicode`). Имена файлов ASCII.
ACL на файлы документов работает (401 без токена). Испорченный портальный токен отклоняется
через `compare_digest`.

**Тесты.** Профильные срезы зелёные: `-k "schedule or dependency or calendar"` — 55 passed;
`-k "portal or export or document_lifecycle or esign"` — 78 passed; `-k estimate` — 19 passed.
**Ни один из блокеров этого реестра не покрыт тестами** — это дыры в покрытии, а не регрессии.
